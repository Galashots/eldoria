## Resolved in this pass

All seven carry regression tests in `tools/playtest-fixes-test.mjs`, wired into `npm test`.
Each test was confirmed to fail against the pre-fix `index.html`.

### ELD-PT-002 — a correct answer now always deals damage

**Root cause.** `answerCombat()` set the per-hit damage and opened the slash window, but
`slashHits` started at 0 and only `executeSlash()` incremented it. A player who answered
correctly and never tapped ended the turn on `slashHits * slashDmgPerHit = 0` damage — and
still took the enemy's full retaliation. A *mashed wrong answer* therefore out-damaged an
*untapped correct one*, which inverts the whole point of the game.

**Fix.** The code now enforces an explicit invariant: **answering correctly always beats answering
wrongly, no matter how fast anyone taps.**

```
correct, zero taps  = 2 x baseDmg   (banked before the window opens)
wrong,  any taps   <= 1 x baseDmg   (hard cap via slashDamageCap)
```

The floor on a right answer is strictly above the ceiling on a wrong one. Tapping still scales
without limit on a correct answer, so it remains rewarding; it simply can never turn a wrong
answer into the better play. A wrong answer keeps a small consolation payout — losing is
deliberately never punitive in this game — it just cannot out-earn knowing the answer.

The first version of this fix only removed the zero-damage case, which left the original
incentive inversion intact: three mashed taps on a wrong answer still beat one untapped correct
answer. That was caught in non-author review and is now covered by a test that mashes 200 taps
on a wrong answer, far beyond any human rate, and asserts it still loses.

**Not done here:** the tracker also asks for a no-mash option. The invariant above is what makes
the game fully playable without one — a player who never taps at all now wins fights by answering.
Combat is already player-paced with no timer; a separate reduced-dexterity/input-pace setting was
considered and is not needed for this audience.

### ELD-PT-003 — the Mine is a cavern again

**Root cause.** `buildMineMap()` flood-filled the zone with `TREE` and carved the track out of
`PATH`. The comment even called them "rock pillars", but the renderer drew them with the forest
tile and the forest palette, so the endgame zone and its boss fight took place in a hedge maze.

**Fix.** Two new tile types, `ROCK` (blocking cavern wall) and `CAVE` (walkable cavern floor),
with drawn fallbacks: faceted rock with a warm upper-left key light matching the Visual North
Star, occasional teal crystal seams that tie to the Crystal Wyrm, and a dark floor with grit and
mine-track sleepers. `assets/rock.png` and `assets/cave-floor.png` are registered but absent, so
real art upgrades the zone with no code change. Tile ids are never serialized — area maps are
rebuilt from their `build*Map()` function on load and only crop state is saved — so appending
ids is save-safe. Deep Woods and Wilds keep their trees; a test asserts it.

**North Star alignment.** Moves toward it. The Mine now has its own palette, light direction, and
floor language instead of borrowing the forest's. It remains placeholder-tier drawn art, so the
zone is still inside the documented interim gap (ELD-PT-009) — this fix removes a *wrong* reading,
it does not deliver final art.

### ELD-PT-004 — combat no longer leaves the HUD or the save stale

**Root cause.** `nextCombatTurn()` refreshed the combat modal's bars but never the world HUD.
`eatInCombat()` spent an item and changed HP without updating or saving. `fleeCombat()` closed
the modal and did neither. So the HUD could show pre-combat health and pre-consumption food, and
a reload mid-fight handed the food back.

**Fix.** `nextCombatTurn()` now refreshes the world HUD; `eatInCombat()` persists immediately;
`fleeCombat()` refreshes and persists on the way out. Victory and defeat already did both.

### ELD-PT-005 — the visible silhouette is tappable

**Root cause.** A tap resolved to exactly one tile: the one under the finger. Sprites and prisms
are drawn taller than the tile they stand on, so an NPC's head and body hang over the ground
behind them and a tap there resolved to empty ground.

**Fix.** `interactAtVisibleTile()` tries the tapped tile first — so a base tile always beats
anything overhanging it, and neighbours can never steal each other's taps — then walks up to
`TAP_REACH` (2) steps down-screen to find the base of the silhouette actually touched. One step
down-screen differs by projection: top-down it is the next row, but iso screen-y is `(px + py) / 2`,
so it advances row *and* column together. The existing "a distant tap does not bypass walking to
her" guard still passes, and a new test asserts a far tap is not captured.

### ELD-PT-007 — one source of truth for equipment

**Corrected scope.** See the verification summary: the reload path already worked. The real
defect was that `VISUAL_EQUIPMENT` duplicated `player.gear`, so the two could only stay in step
as long as every future writer remembered a manual sync call.

**Fix.** `VISUAL_EQUIPMENT` and `setVisualEquipment()` are deleted. `hasVisualEquipment(slot)`
derives the answer from `player.gear` on demand. Boot, import, equip and profile-switch are all
correct for free because they all set `player.gear`. A test asserts that clearing a gear slot
clears the layer with no sync call — the assertion the old stored-flag design would fail.

### ELD-PT-014 — the store prompt names its measure (partial — see ELD-PT-014a)

**Root cause, worse than reported.** The playtest said "most normal crops have the same absolute
margin". In fact *four of five* are identical: turnip, carrot, corn and pumpkin all profit exactly
+1 per harvest; only starfruit differs at +2. Meanwhile profit *per second* is won by turnip. So
"which seed makes you the most gold?" had two defensible answers and no way to tell which was meant.

**Fix.** The prompt now reads "Which seed earns the most gold profit per harvest? (sell price −
seed cost)", spoken in both profiles. That names the measure and the time horizon, and has the
single unambiguous answer starfruit.

**Residual split out as ELD-PT-014a, not silently closed.** The acceptance criteria also ask the
game to "explain why the correct choice wins". That half is **not** done, so per this tracker's own
rule the finding cannot be called Resolved. The store has no answer-check surface — the prompt is
rhetorical, there is no selection to respond to — so there is nowhere to attach that feedback
without inventing a new mechanic, which would be scope this PR has no mandate for. The shop rows
deliberately still show both operands (cost and sell price) and not the difference, so the
subtraction stays the player's to do.

### ELD-PT-015 — the playfield fits under the HUD

**Root cause.** `#game.iso-mode` asked for `height: 100dvh` while sitting inside `#stage`, a
`100vh` flex column that already contained the in-flow HUD. The canvas therefore overflowed by
exactly the HUD's height — the reported 57px at 1363×936.

**Fix.** The canvas is now `flex: 1 1 auto; min-height: 0`, so `#stage` hands it whatever is left,
and `#stage` itself uses `100dvh` (with a `100vh` fallback declared first) so the column tracks the
mobile URL bar. `applyCanvasMode()` reads the resulting box, so the backing store and view rows
follow automatically. Tested at desktop, iPad landscape and phone portrait.

## Open — blocked on an owner decision

These are product and pedagogy calls, not defects with a correct implementation. Each is left
untouched deliberately.

- **ELD-PT-001 — replace overt quizzes with embedded learning.** This is a redesign of the core
  loop, not a fix. It needs a decision on what the first Farm→Town→Wilds arc *becomes* before any
  code moves, and it interacts with ELD-PT-010. Recommend brainstorming it as its own spec.
- **ELD-PT-006 — Character & Inventory screen.** Well specified in the report (≈75% Diablo III /
  25% Minecraft, paper doll, compare-then-equip). It is a whole new screen plus an item-model
  change; it should be its own design and plan cycle, and the report itself recommends sequencing
  it after the state fixes — which are now done.
- **ELD-PT-010 — scaffolded wrong-answer retry.** The three-strike hint ladder is a pedagogy
  design, and it should be designed together with ELD-PT-001 so the two do not contradict.
- **ELD-PT-013 — dumpling gacha pressure.** Owner-decided in the creative direction (§21):
  earned-gold pulls remain; rarity, pity, and the 18 collectibles remain; pressure mechanics
  are removed (no discounted multi-pull bundle, no "save up for a better deal" nudge);
  deterministic dough paths and visible odds in plain language are approved. No real-money
  purchase, daily-login pressure, or timed offer, ever. Implementation details remain open.

## ELD-PT-011 — owner-scoped, 2026-07-29

Leo answered a scoping pass on 011/012/006. The answers below are **decisions**, not
proposals.

**Scope rule Leo set: only what his two children actually hit.** ChatGPT's list (text
scale, captions, reduced motion, contrast, read-aloud) is deliberately *not* being built.
It is not rejected — it is unevidenced for this audience, and an accessibility panel full
of controls nobody needs is a worse surface than a small one that solves real problems.
Anything on that list goes in when it is observed to be needed.

A separate reduced-dexterity/input-pace setting was considered and is not needed. Combat
is already player-paced with no timer; a player who never taps wins by answering correctly
(see ELD-PT-002).

Three observed problems, and what each becomes:

**1. Sound mix.** One on/off toggle is not enough — music drowns speech and the whole
thing is too loud in a quiet room. Build **separate music / speech / effects levels**,
persisted per profile. Three channels is the accepted implementation choice because music,
speech, and effects have different user needs: a child may want game sounds quiet while
keeping spoken instructions audible, or may want music off entirely during focused play.

Acceptance criteria:

- each channel's slider changes only its own audio category;
- zero fully mutes that channel;
- levels persist per profile without leaking between profiles;
- speech level affects automatic speech and "say it again" consistently;

**2. Missed spoken instructions.** Every spoken instruction must also exist visibly on
screen — **audio is never the only channel** — plus a **"say it again" speaker button**
next to the current instruction, which re-reads on demand. Chosen over a persistent goal
bar and over auto-repeat: the child controls it, and nothing ever repeats unasked.

Acceptance criteria:

- every spoken instruction also appears visibly;
- "say it again" repeats the current instruction on demand and does not replay stale text;

Note this deliberately does *not* close ELD-PT-012. A goal bar would have covered both;
Leo chose the narrower control, so onboarding remains its own item.

**3. TTS spam on fast tapping.** Leo's younger son taps quickly to buy several crops and
the speech re-triggers on every tap. **Decision: routine actions are not spoken at all.**

TTS allow-list (spoken): instructions, quest dialogue/text, and story.
TTS silent-list: purchases, pickups, routine confirmations, and other ordinary repeated
actions — unless later added deliberately.

Chosen over interrupt-and-replace, over same-line suppression, and over a shop-speech
toggle — those all manage the noise, this removes the cause, and it makes speech mean
"this matters" wherever it occurs.

Acceptance criteria:

- rapid interaction does not stack routine speech;
- purchases, pickups, and other routine confirmations produce no speech at any tap rate;
- test it by mashing, the way a six-year-old does.

### ELD-PT-011a — bulk buy in the shop

Owner-observed, not in ChatGPT's report. Buying a lot of crops means one tap per crop.

- Quantity options **1 / 5 / 10 / 15 / 20**, as Leo specified.
- **Affordability: buy the affordable partial amount.** Tap "buy 20" with gold for 12 and
  the shop buys 12, clearly showing the actual amount bought.
- **Zero-gold case:** if the player can afford zero, the tap must remain responsive and
  show a brief "Need more gold" message rather than silently doing nothing. A silent dead
  tap is what the younger child reads as the game being broken.
- The count shown must be the count bought. That is the whole risk of this choice.

Filed as its own ID because it is shop UX, not accessibility, even though it surfaced
during the accessibility pass and shares the TTS fix.

## Retest protocol

Unchanged from the source report. When an item is claimed fixed: record the commit/PR here, run
the finding's original reproduction steps, run `npm test`, exercise both profiles on desktop,
iPad landscape and phone portrait, and mark **Resolved** only when the acceptance criteria pass.

**Note on running the suite locally:** `npm run assets:build` fails on Leo's Windows box because
the canvas golden files are rasterized on CI. That is expected and is not a broken branch — see
`AGENTS.md`. `gh run list` is the authority. The game-behaviour tests (`smoke-test.mjs`,
`iso-test.mjs`, `playtest-fixes-test.mjs`) can be run directly and do pass locally.
